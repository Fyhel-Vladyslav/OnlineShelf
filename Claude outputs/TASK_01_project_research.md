## 1. Контекст

Репозиторій `OnlineShelf` — практична частина магістерської роботи «Інтелектуальний сервіс формування та візуалізації рекомендацій гардероба (Smart Outfit Recommender)», НУВГП, гр. КН-61м.

**Що заявлено в звіті з передкваліфікаційної практики (цільова архітектура):**

- **Стек:** .NET 8 / ASP.NET Core, FastEndpoints (REPR), Ocelot API Gateway (JWT, REST назовні), gRPC всередині, PostgreSQL + EF Core 8 (Code-First, міграції), S3/MinIO для зображень, React UI.
- **Сервіси:**
  1. **Gateway** (Ocelot): єдина точка входу, JWT, маршрутизація.
  2. **User Service**: профілі, налаштування, стильові пресети.
  3. **Image Service**: приймає multipart, працює з S3; gRPC: Upload, GetByName, Delete, GetCrop.
  4. **Crop Image Service**: YOLO / SAM / RemBg, видалення фону, обрізання (BBox/Mask).
  5. **Parse Image Service**: визначає тип, колір, матеріал і рахує мультимодальний ембединг `x_i`.
  6. **Shelfs Service**: полиці, речі (`ItemDto`), зберігання ембедингів (`real[]`, згодом pgvector); REST+gRPC.
  7. **Outfit Offer Service**: оркестратор генерації образу, черги, погода (Open-Meteo, In-Memory cache TTL 30–60 хв + SemaphoreSlim проти thundering herd, округлення координат).
  8. **Outfit Offer Network**: CSP-фільтр, GNN-скоринг сумісності, Gap Analysis, задачі на VTON-візуалізацію.
- **Сценарій А (оцифрування речі):** UI → Gateway → Shelfs → gRPC Image → Crop → S3 → Parse (метадані + ембединг) → Shelfs → PostgreSQL → UI.
- **Сценарій Б (генерація образу):** `POST /api/outfits/offer` → Outfit Offer → погода з кешу → гардероб з ембедингами зі Shelfs → CSP-фільтр → GNN / Beam Search → скор `S` → Gap Analysis при `S < S_threshold` (віртуальний айтем `IsVirtual = true`) → швидка відповідь за 200–300 мс → асинхронна задача VTON через Queue/Worker → SignalR/Polling.
- **Математична модель:** образ `O = ⟨top, bottom, shoes, outerwear?⟩`. Прохід 1: булеві обмеження `C_j`. Прохід 2: `S = (Σ w_p·x_p) · Π C_j`, `S ∈ [0,1]`.
- **Ключові вимоги:** FR-1…FR-5 (гардероб, автодетектування, UI Wizard з кроками Context/Include/Exclude/Reference, генерація образу, поради «докупити»). NFR-1: ≤ 500 мс без VTON. NFR-2: координати тільки в пам'яті. NFR-3: горизонтальне масштабування.
- **Інноваційні фічі (план):** Weather Feedback Loop, Multi-Location Closet Tracking (статуси доступності речей), Wishlist Cohabitation + VTON, асинхронна візуалізація.

**Наступний етап розвитку** описано у файлі `outfit-compatibility-scoring-theory.md` у корені репозиторію. **Прочитай його повністю.** Коротко: скорер `IOutfitScorer` на основі Type-Aware / CSA-Net підпросторів для попарної сумісності та GNN (NGNN) для агрегації на рівень образу. Навчання спершу на Polyvore Outfits, потім донавчання на власному датасеті. Ембединг `x_i` рахується один раз у Parse Image Service і кешується.

## 3. Що дослідити

### 3.1. Фактична структура
- Для кожного сервісу в `backend/Microservices/` (Gateway, ImageService, ShelfsService, UserService, OutfitOfferService, OutfitNetworkService, ParseImageService): мова/фреймворк, точки входу, ендпоінти (REST / FastEndpoints / gRPC, з файлами `.proto`), залежності від інших сервісів, база даних, конфігурація в `docker-compose*.yml`.
- `ocelot.json` / `OcelotConfigs`: які маршрути реально є.
- `frontend/admin-portal`: що це за застосунок, які API викликає.
- `.github/workflows`: що робить CI.

### 3.2. Порівняння «заявлено ↔ реалізовано»
Таблиця з рядками для кожного сервісу, кроку сценаріїв А і Б, FR/NFR та інноваційної фічі. Колонки: **Статус** (✅ готово / 🟡 частково / ❌ немає), **Де в коді** (файли), **Коментар**.
Окремо перевір:
- чи існує **Crop Image Service** (у звіті він є, а в `Microservices/` окремої папки немає, можливо, логіка всередині ParseImageService чи ImageService);
- чи реалізовані gRPC-виклики зі сценарію А і як вони називаються насправді;
- модель айтема в Shelfs: чи збігається з `WardrobeItemDto` з теоретичного файлу, **чи є поле для ембединга** і якого типу;
- погода, кешування, SemaphoreSlim, JWT, S3/MinIO: є чи ні.

### 3.3. Готовність до наступного етапу (GNN-скорер)
- Що саме повертає ParseImageService зараз (класи, атрибути, чи є ембединг, яка модель: `classes.json`, `app/`, `proto/`, `requirements.txt`).
- Чи є в OutfitOfferService / OutfitNetworkService інтерфейс на кшталт `IOutfitScorer`, заглушки, CSP-фільтр, Beam Search.
- Як ембединг має проходити шлях Parse → Image → Shelfs → Outfit Offer. Які контракти (proto/DTO/міграції) доведеться змінити.
- Де краще запускати Python-модель GNN: окремий Python-сервіс через gRPC, ONNX у .NET чи щось інше. Дай аргументи «за» і «проти» з урахуванням поточного коду.

### 3.4. Якість і ризики
Коротко, до 10 пунктів: невідповідності назв (напр., `AttributeMatterial`), мертвий код (`WeatherForecast.cs`, `1.txt`), відсутні тести, захардкоджені значення, проблеми безпеки, розбіжності між `docker-compose` і реальними портами.
